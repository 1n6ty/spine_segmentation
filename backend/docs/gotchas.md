# Known Gotchas

Non-obvious failures encountered in this project. Check here first when something breaks
in an unexpected way.

**Maintenance:** Add a row whenever a new non-obvious failure is found during development
or code review. The goal is that the next agent or developer hits this table before they
hit the bug.

| Symptom | Cause | Fix |
|---|---|---|
| A detail route keyed by a non-integer, non-slug PK (e.g. a dotted DICOM SOP Instance UID) 404s for real values but passes tests using dot-free fixtures | DRF's `DefaultRouter`/`SimpleRouter` defaults `lookup_value_regex` to `[^/.]+`, which excludes `.` — the URL never matches, so the view never runs | Set `lookup_value_regex` explicitly on the ViewSet (`r'[^/]+'` is safe since PKs never contain `/`) — see `Dicom/v1/views/dcmparse.py`'s `DcmViewSet` and `Company/v1/views/company.py`'s `lookup_value_regex`/`lookup_url_kwarg` for the same pattern with a numeric-only regex |
| A migration that runs `RunPython(fn)` where `fn` does raw `schema_editor.execute(...)` DDL raises `TransactionManagementError: Executing DDL statements while in a transaction on databases that can't perform a rollback is prohibited` — but only against real MySQL, never SQLite, and only on a genuinely fresh database (an already-migrated dev volume with that migration pre-recorded as applied never re-runs it, so this can stay hidden for a long time) | `RunPython`'s callable executes inside its own atomic savepoint, nested inside the migration's own atomic block; MySQL/InnoDB can't roll back DDL inside a transaction | Use `migrations.RunSQL(sql=..., reverse_sql=...)` instead — it executes directly against the schema editor with no extra atomic wrapping. If the SQL is vendor-specific (see next row), branch on `django.db.connection.vendor` at migration-*load* time to build the SQL string, since `RunSQL` takes a literal string, not a per-vendor callable — see `Profile/migrations/0002_auth_user_email_ci_unique.py` |
| A migration is recorded as applied (`django_migrations` has the row) but the table/column it should have created doesn't actually exist on a real, persistent dev/CI database volume | The migration file was edited in place after already being applied once (e.g. a `CreateModel`'s fields were extended, or a whole new `CreateModel` operation was appended into an existing migration) rather than adding a new migration file — Django tracks applied-ness by `(app, name)`, not by file content, so it never notices the file changed | Don't hand-edit an already-applied migration's operations; add a new migration instead. To repair an already-drifted volume without wiping it: use `django.db.connection.schema_editor()` to `create_model()`/`add_field()` directly from the real current model class (guaranteed-correct DDL, no manual SQL) for just the missing pieces, then leave `django_migrations` alone |
| `./manage.sh test-e2e` (or any manual bring-up) times out waiting for the autofill loader forever, no error | `api-celery` isn't a dependency of `api`/`nginx`/`traefik` in `compose.dev.yml` at all, so nothing brings it up implicitly — `segment_vertebraes` (async Celery task) never gets consumed, and the SSE status stream just sits on `segmentation.processing` | Bring up `api-celery` explicitly alongside `api nginx traefik` — already fixed in `manage.sh`'s `test-e2e` action |
| A real, freshly-served page in a Playwright test against `./manage.sh test-e2e`'s stack renders completely blank, or the DICOM upload step silently never proceeds | Frontend's `FileCache` uses the Cache Storage API, only available in a browser "secure context" (HTTPS, or literal hostname `localhost`) — hitting the stack over plain `http://nginx` from inside the Docker network leaves `window.caches` undefined and the relevant `async` call throws into an unhandled rejection with no visible error | Use `https://traefik` instead (Traefik's dev router matches any Host header, self-signed cert, `ignoreHTTPSErrors: true` in the Playwright config) — already fixed in `manage.sh`'s `test-e2e` action and `frontend/playwright.live.config.ts` |
| Bumping `SEGMENTATION_PIPELINE_VERSION` (`Dicom/utils/constants.py`) doesn't immediately re-segment anything | Re-runs are lazy — a stale-version `DicomImage` is only re-dispatched on its *next* `/api/dcm/parse/` (`Dicom/utils/parse.py`'s `_segmentation_is_stale`). There is no beat sweep and (deliberately) no data migration backfilling existing rows | Expected. Re-fetch/re-upload the affected files to refresh them; if a mass refresh is ever needed, add a one-off management command that enqueues `segment_vertebraes` for rows below the current version |
| Staleness check in `Dicom/utils/parse.py` uses a Python `!=` comparison, not `.exclude(segmentation_model_version=CURRENT)` | Django's `exclude()` on a nullable column does **not** match rows where the column `IS NULL`, so a pre-versioning / never-versioned row (`NULL`) would be silently treated as up-to-date | Keep the comparison in Python (`_segmentation_is_stale`); only the positive reuse filter (`...=CURRENT`) belongs in the ORM query |
