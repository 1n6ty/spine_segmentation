# Gaps & recommendations

Prioritized, ticket-shaped. Each item links to the doc with full detail.

## P0 — blocking or clinically risky

1. **Backend segmentation/parse utilities deleted from disk.** `backend/Mainland/Dicom/utils/parse.py` and `Dicom/utils/segmentation/*` are unstaged-deleted while still imported by `views/dcmparse.py` and `tasks/segmentation.py`. Both `/api/dcm/parse/` and the WebSocket segmentation route crash as a result. Blocks all real frontend↔backend integration. Backend-side fix, not frontend — but everything else in this list that depends on integration is blocked by it. → [backend-integration.md](backend-integration.md)

2. ~~Report page has zero dynamic content.~~ **Done.** The report page is now wired to a real rule-based diagnosis engine (`medical-parameters/diagnosis/`), with a clickable TOC, collapsible regions, a responsive toolbar, and bilingual output. → [diagnostic-pipeline.md](diagnostic-pipeline.md), [clinical-rules-reference.md](clinical-rules-reference.md)

3. **`xraysockets.store.ts` has a broken import.** `import { autoPolygons } from "../study/study.store"` points at a file that doesn't exist anywhere in the repo. Currently silent (dead code, nothing imports this store), but it will break the build the instant the commented-out integration code is re-enabled. → [backend-integration.md](backend-integration.md)

4. **No real authentication.** The `(authenticated)` route guard's redirect logic is fully commented out; the login form has no submit handler. Any visitor reaches PHI-bearing pages today. Should be fixed before any use with real patient data. → [security-privacy.md](security-privacy.md)

## P1 — significant functional gaps

5. **Zero live backend wiring.** All API calls (`dicomParser.ts`) and the WebSocket hookup (`xraysockets.store.ts`) are commented out. The intended "AI auto-segments, doctor corrects" workflow doesn't happen — every vertebra polygon must be hand-drawn in `edit` today. → [backend-integration.md](backend-integration.md)

6. **PDF/DOCX export not implemented.** The report page's export buttons are present but disabled — generating real downloadable files was explicitly scoped out of the diagnosis-engine work and remains a separate follow-up.

7. ~~`segments` parameters likely never populate on the `measure` page.~~ **Done, then refined twice more after user testing.** `structures[projection].segments` now returns up to 3 standard segments (Cervical C2-C7, Thoracic Th1-Th12, Lumbar **L1-S1**). Two follow-up corrections after the initial "3 fixed segments" implementation: (a) the lumbar range was originally L1-L5 reusing the diagnosis engine's `regions.ts`, but the clinically-standard "global lumbar lordosis" range is L1-S1 (includes the sacrum) — this consumer now has its own range definitions, separate from `regions.ts`, since the two need different boundaries; (b) segments originally required *all 24* vertebrae annotated before *any* segment showed up — now each of the 3 is gated independently by matching vertebra `id`s, so e.g. an L1-S1-only annotation shows the lumbar segment immediately without needing the rest of the spine. The dynamic `addSegment`/`removeSegment` mechanism (which nothing called) was removed. The frontal-plane arc-detection algorithm in [clinical-rules-reference.md](clinical-rules-reference.md) remains unimplemented — it would still be needed to upgrade the report's frontal-plane scoliosis grading from fixed-region approximation to true detected-curve grading, but is a separate, larger piece of work.

8. **Report's left/right labeling**, found during the measurements-tab calculator audit (see item 14/16 below):
   - ~~Confirmed bugs: frontal scoliosis "left-sided" and sagittal "lordosis-flattening" branches were unreachable.~~ **Fixed** — `segments.ts`'s `p3` (central angle) is now signed via the fitted circle's actual center, not the unsigned law-of-cosines `acos`. Verified with synthetic left/right-bulging arcs. → [clinical-rules-reference.md](clinical-rules-reference.md)
   - Still open: general approximation risk — labels are based on the sign of computed angles/offsets assuming the source clinical documents' sign convention matches this app's pixel coordinate system; not validated against real images (no DICOM laterality metadata tracked). The documents' own explicit sign-convention note ("negative = clockwise from vertical") was confirmed and matched during the fix, which reduces but doesn't eliminate this risk.
   - Still open: L5 spondylolisthesis grading's input (`gaps.ts`'s `p7`) is now correctly signed (verified an unslipped baseline reads "normal," not severely pathological), but `p7` only responds to *rotation* between L5 and S1, not the *translational* slip spondylolisthesis fundamentally is. May need a different input parameter (`p5`/`p6`) — domain input needed, not a pure code fix. → [clinical-rules-reference.md](clinical-rules-reference.md)

9. **`FileCache` orphan-on-TTL-expiry.** The 24-hour IndexedDB session sweep doesn't clean up the corresponding Cache Storage API file entries, unlike the explicit `delete()`/`clearAll()` paths which do. PHI can persist past its intended retention window. → [security-privacy.md](security-privacy.md)

## P2 — worth doing, not urgent

10. ~~Near-zero test coverage~~ **Further addressed.** `medical-parameters/diagnosis/rules/{sagittal,frontal}.test.ts` cover every grading function, and `medical-parameters/calculators/{vertebras,gaps,segments,spine}.test.ts` now cover the calculator layer too (85 tests total, including new sign-direction cases for every angle made signed in item 16). `shared/geometry/geometry.ts`'s primitives are still untested directly (only indirectly, through the calculator tests). → [testing-strategy.md](testing-strategy.md)

11. **Unused Cornerstone.js dependency.** `@cornerstonejs/core` and `@cornerstonejs/dicom-image-loader` are installed but never imported; DICOM rendering is a separate hand-rolled canvas pipeline. Either finish the planned integration or drop the dependency. → [architecture.md](architecture.md)

12. **Naming collision risk.** `features/dicomParser.ts` (commented backend calls + `formatJson2Polygons`) and `features/dicom/parser.ts` (actual DICOM tag extraction) are easy to confuse by name despite very different responsibilities. → [architecture.md](architecture.md)

13. **Several clinical-rule tables are intentionally not implemented**: the sagittal disc-angle-by-vertebral-level norm table (now cleanly re-extracted from the original `.docx`, but its magnitude doesn't match any parameter currently computed — needs your input on the exact geometric definition before it can be wired up, not a transcription problem anymore); the angular focal-kyphosis table (needs a "deformed segment" identification step not derivable from fixed regions); the cervical-specific sagittal dislocation/subluxation/fracture/disc-rupture diagnosis codes (reference undefined "parameters 1-8"); the vertebral-body-height norm table (confirmed genuinely blank in the original source, not garbled — nothing to extract). → [clinical-rules-reference.md](clinical-rules-reference.md)

14. ~~`gaps.ts` disc-height/wedging/displacement formulas were badly wrong.~~ **Done** (corner-pairing and vector-mismatch parts; the p1/p5 slot-swap part was *not* actually done on the first attempt — see item 16). A systematic audit (cross-checking every parameter in all 4 calculators against its `config.ts` description, verified numerically with known synthetic geometry, not just by reading) found `p2`/`p3` ("anterior/posterior disc height") pairing the wrong corners across adjacent vertebrae — in a test case with a known 10px disc gap, the old formula returned 130 instead of ~10. `p4`/`p6` inherited the same corner-pairing bug. `p7` had its compared vectors mismatched relative to its label. All fixed; `vertebras.ts`/`segments.ts`/`spine.ts` were audited the same way and found correct. → [diagnostic-pipeline.md](diagnostic-pipeline.md)

15. ~~Inclination-angle formulas used an inconsistent sign/zero-point convention.~~ **Done.** `vertebras.ts` (p6-p9), `segments.ts` (p4), and `spine.ts` (p1) used ad-hoc `atan2`/`asin` calls where a perfectly vertical edge read as 180° instead of 0°, and clockwise/counter-clockwise sign was inconsistent. Replaced with `geometry.ts`'s `getSignedAngle(reference, edge)` (the same helper `orderer.ts` already used correctly for point ordering) so every signed angle now follows standard mathematical convention: 0° aligned with the named reference axis, positive for counter-clockwise rotation, negative for clockwise. Verified empirically with known tilted geometry before and after the fix. → [diagnostic-pipeline.md](diagnostic-pipeline.md)

16. ~~The remaining "magnitude-only" angles (wedging, central angle, intervertebral angle, etc.) were unsigned.~~ **Done.** Every angle the calculators compute is now signed (-180°..180°, CCW-positive), not just the inclination-style ones from item 15. `vertebras.ts` (side `p5`, frontal `p6`), `gaps.ts` (`p4`,`p5`,`p6`,`p7`), and `segments.ts` (`p3`, redesigned to use the fitted circle's actual center instead of the sign-blind law-of-cosines `acos`) all switched from `angleBetweenVectors`/`acos` to `getSignedAngle`. Vector order for each was chosen and verified against either an explicit clinical convention (frontal vertebral wedging: "base right = positive" from the source document) or a sensible baseline-must-read-normal check (L5-S1 angle). This is what made item 8's two confirmed bugs fixable. → [clinical-rules-reference.md](clinical-rules-reference.md), [diagnostic-pipeline.md](diagnostic-pipeline.md)

17. ~~`gaps.ts`'s `p1`/`p5` slot-swap "fix" (item 14) wasn't actually applied.~~ **Done, for real this time.** The first pass correctly *diagnosed* that `p1` should hold the angular intervertebral angle and `p5` the linear displacement (per `config.ts`), but when the formulas were rewritten the underlying *values* were never actually moved between the two slots — `p1` kept holding the (legitimately signed, sometimes negative) displacement value while still being labeled "Intervertebral angle." Caught when a displayed "Anterior disc height" showed a negative number on the `measure` page. Fixed by actually swapping which formula populates which slot; `diagnosis/store.svelte.ts`'s frontal-displacement consumer updated back to read `p5`; `gaps.test.ts` assertions updated. → [diagnostic-pipeline.md](diagnostic-pipeline.md)

18. ~~`Table.svelte` showed parameter values under the wrong column headers.~~ **Done — independent bug, found while investigating item 17.** Header columns are grouped by type (`linear` first, then `angular`, per `config.ts`), but row values were rendered in raw `p1..p7`/`p1..p9` order with no matching regroup. For `vertebras` and `segments`, the type sequence happens to already be a contiguous linear-then-angular run, so this was invisible — but `gaps` (linear params at non-contiguous `p2`,`p3`,`p5`) and `overall` (linear at `p2`,`p3`, angular at `p1`) were both silently column-shifted. This is what made item 14's `p2`/`p3` disc-height columns show `p1`'s displacement value instead, and would have made the Spine tab's "trunk axis length" column show an angle value. Fixed by deriving the row-value order from the same `head`-based type grouping the headers use, so both are built from one source of truth instead of two that can drift apart. → [diagnostic-pipeline.md](diagnostic-pipeline.md)

19. **Vertebra naming is purely positional and assumes contiguous bottom-up annotation — surfaced while building per-segment gating (item 7).** `editor/logic/orderer.ts`'s `orderAndName()` always assigns `vertebraeNames[0]` ("S1") to whatever vertebra has the highest Y (lowest on screen) among the *currently annotated set*, regardless of how many vertebrae actually exist or what they really are anatomically. This works correctly as long as you annotate from the true bottom (S1) upward — verified live with a 6-vertebra L1-S1-only annotation. But annotating an *isolated* region with nothing below it (e.g. only cervical vertebrae, no thoracic/lumbar/sacral) would mis-name the bottommost one "S1." Not a bug in anything built so far (everything here assumes/requires bottom-up annotation), but a real limitation worth knowing about before relying on partial, non-bottom-anchored annotation for anything. Fixing it properly would need anatomical landmark recognition, not just positional inference — a much larger undertaking than anything in this list. → [diagnostic-pipeline.md](diagnostic-pipeline.md)
