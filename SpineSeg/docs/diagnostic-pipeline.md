# Diagnostic pipeline

The app's purpose is a 5-screen flow: upload a spine X-ray, verify the patient, annotate/correct vertebra outlines, review computed geometric parameters, and get a text-based first diagnosis. This doc walks each screen with exact file references, then documents precisely what the medical-parameter calculators compute. The report screen's diagnosis-text engine is documented in detail in [clinical-rules-reference.md](clinical-rules-reference.md).

## 1. Upload (`routes/[lang]/+page.svelte`)

`DicomUploadCard` (`components/ui/DicomUploadCard/`) and `Sessions/Manager.svelte` + `Card.svelte` (session list). Selecting a file calls `SessionService.uploadFile(file, projection)` (`core/session/session.svelte.ts`), which:
1. Hashes and stores the raw file via `FileCache.save` (Cache Storage API).
2. Reads it into an `ArrayBuffer` and parses it immediately, client-side, with `dicom-parser` (`dicomParser.parseDicom(...)`).
3. Wraps the parsed dataset in a `PatientService`.
4. Debounce-saves session metadata to IndexedDB via `registry`.

No AI segmentation happens at this point — see [backend-integration.md](backend-integration.md) for why.

## 2. Patient (`(authenticated)/patient/+page.svelte`)

`PatientInfo.svelte` / `InfoBlock.svelte` render `project.session.mergedPatient` / `mergedStudy` / `mergedSeries`. Fields are pulled straight from DICOM tags in `features/dicom/parser.ts`:

- `parsePatientFromDicom`: PatientUID (`x00100020`), name (`x00100010`), birth date (`x00100030`), sex (`x00100040`).
- `parseStudyFromDicom`: study UID (`x0020000d`), study date (`x00080020`), description (`x00081030`), physician name (`x00080090`), institution name/address (`x00080080`/`x00080081`), station name (`x00081010`).
- `parseSeriesFromDicom`: series UID (`x0020000e`), modality (`x00080060`), body part (`x00180015`).

If both projections are loaded and one is missing a field, `mergedPatient`/`mergedStudy`/`mergedSeries` (the `$derived.by` getters in `SessionService`) fill it from the other.

## 3. Edit (`(authenticated)/edit/+page.svelte`)

Renders one `XrayEditorCard` (`components/ui/Editor/Container.svelte`) per loaded projection. This is a hand-rolled 2D canvas editor (not Cornerstone.js — see [architecture.md](architecture.md)):

- `InstanceContainer` (`features/editor/core/instance-container.svelte.ts`) composes three controllers: `nav` (pan/zoom/wheel, `controllers/nav.svelte.ts`), `edit` (point dragging, add/select/delete polygon, draw mode, `controllers/edit.svelte.ts`), `history` (undo/redo, `controllers/history.svelte.ts`).
- `drawMain`/`drawMinimap` (`features/editor/rendering/`) paint the parsed pixel bitmap plus the polygon overlay onto two `<canvas>` elements (main view + minimap).
- Every vertebra is a 4-point polygon (the four body corners). `editor/logic/orderer.ts` and `selection.ts` handle point ordering and hit-testing.
- Editing a point mutates `project.session.projections[projection].polygons` directly; because everything downstream reads from that same reactive array, the `measure` page recomputes instantly.

## 4. Measure (`(authenticated)/measure/+page.svelte`)

The one page that is fully wired to live data. Imports `params` from `medical-parameters/store.svelte.ts`; `Navigation.svelte` switches `params.activeStructure` between `vertebras`/`gaps`/`segments`/`overall`; `View.svelte`/`Table.svelte`/`OverallSpine.svelte` render whichever is active. Recomputation is automatic — Svelte reactivity, no manual invalidation. The `segments` tab shows 3 standard segments (Cervical C2-C7, Thoracic Th1-Th12, Lumbar L1-S1) — previously it was always empty; now each one appears independently as soon as its own vertebrae exist, not gated on annotating the full 24-vertebra spine.

**`Table.svelte` previously showed values under the wrong column headers** for `gaps` and `overall` specifically (not `vertebras`/`segments`): header columns are grouped by type (`linear` then `angular`, per `config.ts`), but row values were rendered in raw `p1..pN` order with no matching regroup — correct only when a structure's type sequence happens to already be a contiguous linear-then-angular run. Fixed by deriving both from the same type-grouped key order, so they can't drift apart again. See `gaps`'s `p1`/`p5` note below for how this combined with a separate calculator bug to look like a negative-height bug.

## 5. Report (`(authenticated)/report/+page.svelte`)

Fully data-driven: a `diagnosis` store (`medical-parameters/diagnosis/store.svelte.ts`) groups the annotated spine into three fixed anatomical regions (Cervical C2-C7, Thoracic Th1-Th12, Lumbar L1-L5 — see [clinical-rules-reference.md](clinical-rules-reference.md) for the full rule engine), evaluates each region/vertebra/gap against threshold tables transcribed from the project's clinical reference PDFs, and assembles a "Diagnostic Conclusion" from whatever is non-normal. The page requires all 24 vertebrae (C2-S1) annotated per projection — if fewer are present it shows a localized "annotate the full spine" message instead of attempting a partial diagnosis.

UI features: a clickable table-of-contents sidebar that scrolls to and expands any region/vertebra/disc; collapsible region blocks with an expand-all/collapse-all toggle; a Lateral/Frontal projection toggle; severity-colored finding cards (normal/grade1-5). The toolbar's action-button cluster is a 2-column grid on narrow viewports and a single row from the `md:` breakpoint up. PDF/DOCX export buttons are present but intentionally disabled — generating real files is out of scope for the diagnosis-engine work and remains a follow-up (see [gaps-and-recommendations.md](gaps-and-recommendations.md)). The disclaimer paragraph ("for educational/screening purposes only... does not replace professional diagnosis") is preserved, now sourced from i18n (`report.disclaimer`) instead of hardcoded.

## Medical-parameter calculators

All four calculator files share the same shape: `get*Params(projection, input, mmPerPixel)` returning `{ name, params: { p1..p9: { val, type } } }`, where `type` is `"linear"` (mm) or `"angular"` (degrees). Geometry primitives live in `shared/geometry/geometry.ts` and `mathjs` is used only inside `solveCircleFit`.

**Point convention (verified, not assumed):** every vertebra's 4 corner points are ordered `[bottom-left, top-left, top-right, bottom-right]`, regardless of the order they were clicked in. This is enforced by `features/editor/logic/orderer.ts`'s `getOrderedReferencePoints()` (re-sorts by signed angle around a down→up axis, run after every polygon add/delete/drag) — confirmed empirically with synthetic click-order and curved-spine test cases, not just by reading the code. All four calculators below assume this convention.

**Angle sign convention:** every angle the calculators compute is signed (-180°..180°), following standard mathematical convention — 0° aligned with a named reference axis where applicable, positive for counter-clockwise rotation as seen on screen, negative for clockwise. This matches the clinical source documents' own stated convention ("Знак (-) отражает угол отклонение прямой от вертикали почасовой стрелке" — negative = clockwise from vertical — see [clinical-rules-reference.md](clinical-rules-reference.md)). Implemented via `geometry.ts`'s `getSignedAngle(v1, v2)` (the same helper `orderer.ts` relies on for point ordering, confirmed CCW-positive empirically). This was applied in two passes: first to the `atan2`/`asin`-based *inclination* angles (which previously had an inconsistent zero-point — e.g. a perfectly vertical edge read as 180° instead of 0°), then to the remaining `acos`-based *wedging/central-angle* measurements that were left unsigned at first (reasoned then that a "magnitude" didn't need direction) — which turned out to be wrong: those magnitude-only values were silently making several diagnosis-engine branches unreachable (see below and [clinical-rules-reference.md](clinical-rules-reference.md)).

- **`geometry.ts`** — `distance`, `vectorSub`, `dotProduct`, `vectorNorm`, `angleBetweenVectors` (acos of normalized dot product, always unsigned 0–180° — no longer used by any calculator, kept for any future case that genuinely wants magnitude-only), `getSignedAngle` (atan2-based, CCW-positive signed angle between two vectors — the one helper now used for every angle below), `angleBetweenPoints` (unused dead export), `getPolygonCenter`, `getMidpoint`, `solveCircleFit` (least-squares fit of `x²+y²+ax+by+c=0` via the normal equations, solved with `mathjs.lusolve`; also exposes the fit's center, `(-a/2, -b/2)`, now used directly by `segments.ts`), `getArcRadius`.

- **`calculators/vertebras.ts`** (`getVertebraeParams`) — per-vertebra, from its 4 corner points. Side projection: `p1`/`p2` superior/inferior endplate length, `p3`/`p4` anterior/posterior body height, `p5` wedging angle (signed angle between the posterior and anterior edge vectors — positive when the posterior edge is taller and the edges converge), `p6`–`p8` contour/endplate inclination to the vertical (Z) axis, `p9` sacral slope to the horizontal (X) axis — computed only when `v.id === "S1"`. Frontal projection: analogous `p1`–`p9` (right/left contour heights, central height via midpoint distance, `p6` frontal wedging angle — verified against the source document's explicit "base right = positive, base left = negative" convention, central-line/endplate inclinations).

- **`calculators/gaps.ts`** (`getGapParams`) — per adjacent vertebra pair (`top` = more superior, `bottom` = more inferior): `p1` intervertebral angle (signed angle between the two vertebrae's own anterior-edge vectors), `p2`/`p3` anterior/posterior disc height (distance between the corners that actually border the disc — top's inferior corner to bottom's superior corner on each side), `p4` disc wedging angle (signed angle between the anterior and posterior disc-border vectors), `p5` linear displacement of the upper vertebra in the disc plane (projection of the anterior disc-border vector onto the top vertebra's own inferior-endplate direction), `p6` angular displacement (signed angle between the anterior disc-border vector and the top vertebra's inferior-endplate direction — ~90° when there's no slip), `p7` a special term active only for the L5–S1 pair (signed angle between S1's own superior-endplate vector and L5's own anterior contour — order chosen so an unslipped baseline reads ~+90°, inside the clinical "normal" band, not a sign-flipped negative that would misclassify it as severe spondylolisthesis). **Previously buggy, fixed in two passes** — `p2`/`p3` paired the wrong corners across the two vertebrae (mixing each vertebra's far corner with the other's near corner), inflating disc-height readings to roughly the combined height of both vertebrae instead of the actual gap; `p7`'s two compared vectors were mismatched relative to its label; all four angular params (`p4`-`p7`) were unsigned — all fixed on the first pass. `p1`/`p5` were diagnosed as swapped relative to their `config.ts` descriptions on that same pass, but the actual *values* were never moved between the two slots until a second pass (caught when "Anterior disc height" displayed a negative number on the `measure` page — see `gaps-and-recommendations.md` item 17). All fixed now, with synthetic-geometry tests in `gaps.test.ts` locking in the corrected behavior including sign direction and the correct slot for each value.

- **`calculators/segments.ts`** (`getSegmentParams`) — given an arbitrary contiguous run of vertebrae (a "segment"): collects all their corner points, fits a circle (`solveCircleFit`), derives `p1` arc radius, `p2` chord length (distance between the segment's end midpoints, capped at the diameter), `p3` central angle, `p4` chord inclination to vertical. `p3` was redesigned from the original unsigned law-of-cosines `acos` formula to `getSignedAngle(start-center, end-center)` using the circle fit's own center — mathematically the same central angle, but now signed: negative when the arc bulges left, positive when it bulges right (verified with synthetic left/right-bulging arcs). This is the lordosis/kyphosis/scoliosis curvature math, and the sign is what the diagnosis engine's left/right and lordosis/kyphosis grading depends on.

- **`calculators/spine.ts`** (`getSpineParams`) — requires ≥24 annotated vertebrae (a fully-marked spine); computes `p1` Th1–L5 trunk-axis inclination to vertical, `p2` trunk-axis length, `p3` a GCoM-style lateral-deviation term (`distance × sin(angle)`, using the same `angle` as `p1`).

- **`medical-parameters/store.svelte.ts`** orchestrates all four: `structures.{side,frontal}.vertebras` reads polygons directly; `.gaps` is auto-derived from adjacent polygon pairs; `.segments` returns up to 3 standard segments (Cervical C2-C7, Thoracic Th1-Th12, Lumbar **L1-S1**), each one independently gated by matching vertebra `id`s (not array position) against a fixed id list — a segment appears as soon as its own vertebrae are present, regardless of whether the rest of the spine is annotated. This is deliberately a *different, narrower* range set than `medical-parameters/regions.ts` (used by the report's diagnosis engine): that one's lumbar region is L1-L5 with S1 handled separately (sacral slope, spondylolisthesis) and requires the full 24-vertebra spine before any region is valid. The id-matching approach relies on `orderer.ts`'s naming being correct, which itself assumes vertebrae are annotated contiguously from S1 upward — annotating an isolated region with nothing below it will mis-name the bottommost vertebra "S1." (The old dynamic `addSegment`/`removeSegment` mechanism, which nothing in the UI ever called, was removed in an earlier pass.) `params.calculate(projection)` combines everything with `mmPerPixel` (from the DICOM `PixelSpacing`/`ImagerPixelSpacing` tag, set in `extractDicomData`, `features/dicom/parser.ts`).

- **`medical-parameters/config.ts`** holds bilingual (`ru-RU`/`en-US`) human-readable names and unit type for every `p1..p9` key, per structure and per projection — this is what `measure`'s `Table.svelte` uses for labels. The `report` page does not reference this file at all currently.
